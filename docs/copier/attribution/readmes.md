# Witing a README

A README file is one of the most important things you can include in a project. We use them to explain the "who, what, where, why" of our projects in plain language. We build them for others, and also for ourselves. How many times have we left a project aside for a week or two, and come back having to spend hours trying to understand what we were doing.

In the age of AI, a README can often provide important context to a project. Taking time to sit down and explain the purpose of a project in plain language, our goals, expected deliverables or products, and ideas about the workflow can save us considerable time in the long run.

So, first and foremost: **Make A README file**

There's a [great answer](https://github.com/orgs/community/discussions/176605) to "What makes a great README" on the Github community forum that explains that a README is there to _build trust_. This is probably one of the most important points, and one we often forget. In choosing between two pieces of software, or analysis, the one that clearly identifies the goals, audience and outputs is going to be chosen. Just because you create something that works doesn't mean people will use it. They have to trust it works, and understand why and how it works for them.

## Make a README File

* Add a `README.md` file in the root directory of your project.
  * Your README file should use [markdown](https://docs.github.com/en/get-started/writing-on-github/getting-started-with-writing-and-formatting-on-github/basic-writing-and-formatting-syntax) formatting. Markdown is widely used and fairly simple to adopt. It is a plain text format, so no one needs to have extra software to read it.
  * Stick to critical headings:
    * `# PROJECTNAME`: the first heading should be your project name, followed by a brief description of what the project does.
    * `## Quick Start`: How should someone install/setup and use the project? How do they repeat the analysis you've done?
    * `## Contributors`: Who helped write this project?
    * `## Using this Software`: More detailed than the Quick Start, broader explanation of what the package/project does. This may include some sample output, or a few example scripts or figures.
    * `## Funding`: Research funding is critical for much academic work. It should be acknowledged.

## What Makes a README Good?

[Utrecht University's README guide](https://utrechtuniversity.github.io/workshop-computational-reproducibility/chapters/readme-files.html) highlights the importance of being clear and concise. Let people know the **why** of the project.

* What does this project solve?
* Who should use it?
* Who maintains it (is it maintained?)

Most importantly, if someone were to find your project, is the `README.md` you've provided enough to help someone understand what you've done, re-use your code, and contribute to the project?

## Bits and Bobs

* Add an image, or, if possible, an animated image showing your project in action.
* Add badges. Badges help provide a simple visual guide to your project.
* Add a Table of Contents to make it easier to navigate.
* Let your own personality show through.
